### 第四章：团队工作协议

**团队工作协议 (Team Working Agreement, TWA)**。这不仅仅是一份文件，更是一种团队文化建设的工具，旨在通过建立清晰、共识的互动准则，来预防和解决因误解和期望错位而产生的矛盾，尤其是在代码审查这种协作密集型活动中。

TWA 应该是一份“**活文档 (living document)**” ，能够随着团队、项目和流程的演进而不断迭代和优化 。维护这份文档的最佳方式是将其**置于版本控制系统（如 Git）中**，并使用团队自身的代码审查流程来管理其变更

### **TWA 的关键组成部分**

TWA 应包含以下几个核心部分：

1.  **明确隐含期望 (Making Implicit Expectations Explicit):**

    - **合理响应时间 (Reasonable Response Times):** 团队需要共同定义对于 PR 审查和评论回复的期望时间。这有助于管理个人期望，避免因等待而产生焦虑或不耐烦。
    - **处理“吹毛求疵” (Blocking Nitpicks):** 明确定义什么是“吹毛求疵”（如代码格式、无关紧要的命名偏好等），并制定相应政策 。不应因为这类问题而扣留 PR 的批准。
    - **自我批准 PR (Self-approving PRs):** 制定关于作者是否可以批准自己 PR 的明确政策 。通常应禁止，除非是在有严格记录和流程的紧急情况下。
    - **保持文明 (Being Civil):** 像会议的行为准则 (Code of Conduct) 一样，明确规定团队成员在协作中应有的尊重和行为标准 。

2.  **可参考的政策 (Referenceable Policies):**

    - **审查范围 (What reviewers should look for):** 定义审查者应该关注的问题类型，如“标准问题”（可读性、复杂性）和“棘手问题”（架构问题），同时将“明显问题”（格式、拼写）通过自动化工具在审查前解决。
    - **批准人政策 (Approver Policy):** 清晰说明谁有资格批准 PR 以及需要多少个批准。作者建议至少需要两位批准者 。
    - **团队协议 (Team Protocols):** 包含团队日常运作的规范，如会议准则、沟通偏好等，像一份新成员的“速查表” 。

3.  **维护与执行 (Maintenance and Enforcement):**
    - **违规后果 (Consequences):** 明确违反 TWA 政策的后果，以确保其严肃性和有效性 。
    - **集体所有权 (Collective Ownership):** TWA 是整个团队的责任，所有成员都应是其共同的创建者、执行者和维护者。
    - **持续改进 (Continuous Refinement):** TWA 的任何修改都应通过团队讨论并达成共识，理想情况下通过 PR 提议 ，并需要所有团队成员的批准 。

### **实践性问题**

#### **关于审查流程与期望**

1.  **响应时间：** 我们团队对于一个 PR 的“合理响应时间”具体是多少小时或工作日？对于初始审查、作者修改后的再次审查以及评论区的问答，响应时间的期望是否应该有所不同？
2.  **“吹毛求疵” (Nitpicks)：** 我们如何共同定义“吹毛求疵”？对于代码风格（缩进、空格、命名偏好等）问题，我们的处理政策是什么？是否应该完全通过自动化工具（Linter/Formatter）来解决，并在审查中禁止讨论？
3.  **批准的门槛：** 一个 PR 被扣留批准 (withholding approval) 和被直接拒绝 (rejecting) 的区别是什么？哪些类型的问题（例如：架构缺陷、未满足核心需求）足以成为扣留或拒绝批准的理由？
4.  **自我批准：** 我们是否允许作者批准自己的 PR？如果允许，必须满足哪些极端或紧急条件？这个过程应该如何记录和通报给团队？

#### **关于政策与标准**

5.  **批准人资格：** 我们团队的批准人政策是什么？一个 PR 需要多少人批准 ？ 团队中所有开发者都默认有批准权吗，还是与经验/角色挂钩？ 经理或 QA 角色是否应该拥有批准权？
6.  **审查重点：** 作为审查者，我们应该将精力集中在哪些问题上 ？哪些问题（如代码格式）应该被视为“必须在审查前通过自动化解决”的 ？
7.  **线下讨论：** 当 PR 的讨论陷入僵局或过于冗长（例如，超过 10 条评论仍在讨论同一点），我们启动线下/实时沟通的触发条件是什么？沟通后，应该如何将结论同步回 PR 中以供追溯？
8.  **文档要求：** 对于一个新功能 (feature) 的 PR，附带相应的文档是“必须的”还是“建议的”？我们如何确保文档不会被遗忘？

#### **关于维护与文化**

9.  **TWA 的存放与修改：** 我们决定将 TWA 存放在哪里？（例如，一个专门的 Git 仓库 ）。修改它的流程是怎样的？是否需要所有团队成员都 `approve` 才能合并？
10. **政策的执行：** 如果有成员持续违反我们共同制定的 TWA（例如，总是提交格式混乱的代码、审查超时、评论语气不当），我们的应对措施是什么？第一步是什么？何时需要管理者介入？
